# เช็กลิสต์ลงนามปล่อยเวอร์ชัน (Release Sign-off Checklist)

- โครงการ: ScamGuard (Scam Image Detection System)
- ตำแหน่งไฟล์: tests_all/release_signoff.md
- อ้างอิงแผนหลัก: Document/tests_doc/test_plan/README.md ส่วนที่ 5.3 เกณฑ์การสิ้นสุดและส่งมอบงาน และส่วนที่ 7 กระบวนการจัดการข้อบกพร่อง
- อ้างอิงความครอบคลุม: tests_all/rtm.md (FR 40 รายการ, NFR 15 รายการ, E2E 6 เส้นทาง, Manual 106 TCs)
- อ้างอิงผลรัน: tests_all/tests_report/manual_tests/execution_log.md และ tests_all/tests_report/automate_tests/server และ mobile
- อ้างอิง Bug: tests_all/bug_report_template.md
- สถานะก่อนสร้างไฟล์: ไม่พบไฟล์ release sign-off checklist ใน tests_all และ Document/tests_doc (ค้น signoff และ exit criteria แล้วพบเฉพาะนิยามในแผนหลัก ยังไม่มีเช็กลิสต์ให้ลงนามจริง)

## 1. วิธีใช้เช็กลิสต์นี้

1. กรอกข้อมูลเวอร์ชันในหัวข้อที่ 2 ทุกครั้งที่ขอปล่อย 1 รอบต่อ 1 ไฟล์ย่อยหรือ 1 ชุดต่อท้ายพร้อมวันที่ ห้ามเขียนทับรอบเก่า
2. ตรวจทีละข้อในหัวข้อที่ 3 ถ้าข้อใดไม่ผ่าน ห้ามลงนาม ให้ส่งกลับไป Retest หรือ Regression ก่อน
3. นำตัวเลข Pass Rate มาจาก execution_log.md และรายงาน automate จริงเท่านั้น ห้ามใช้ตัวเลขจากการอ่านเอกสาร
4. รายการ GAP และ Deferred ในหัวข้อที่ 5 ต้องตรงกับ rtm.md ถ้าพบ GAP ใหม่ต้องบันทึกเพิ่มและให้ PM รับทราบ
5. ลงนามครบ 3 ฝ่ายในหัวข้อที่ 6 จึงถือว่าปล่อยได้ ถ้าฝ่ายใดไม่ลงนามให้ระบุเหตุผลและเงื่อนไขค้าง

---

## 2. ข้อมูลรอบปล่อย (กรอกต่อรอบ)

- ชื่อเวอร์ชัน: เช่น v1.3.0
- วันที่ขอปล่อย: ปปปป-ดด-วว
- ขอบเขตที่ปล่อย: ระบุโมดูล เช่น Mobile, Backend API, AI Pipeline, Admin Portal หรือทั้งระบบ
- คอมมิตหรือบิลด์: ระบุรหัสคอมมิต บิลด์ Mobile เวอร์ชันโมเดลที่ Deploy
- สภาพแวดล้อมที่ตรวจรับ: เช่น Staging ก่อน Prod ระบุพอร์ต 8000, 5432, 6379, 5173 และอุปกรณ์ทดสอบ (Pixel 6, Galaxy S21, Emulator API 33 หรือ 34)
- ผู้รวบรวมหลักฐาน: ชื่อ QA ที่รวบรวม execution_log รายงาน automate และรายการ Bug

## 3. เกณฑ์ออกจากแผนหลัก (Exit Criteria ตรวจทีละข้อ ตรงตามแผนหลักส่วนที่ 5.3)

- ข้อ 1: TC ระดับ P0 Blocker และ P1 High ผ่าน 100 เปอร์เซ็นต์ (Pass Rate เท่ากับ 100)
  - ผลจริง P0: ผ่านกี่ TC จากทั้งหมดกี่ TC
  - ผลจริง P1: ผ่านกี่ TC จากทั้งหมดกี่ TC
  - ผ่านเกณฑ์หรือไม่: ผ่าน หรือ ไม่ผ่าน
- ข้อ 2: TC ระดับ P2 Medium ผ่านไม่ต่ำกว่า 95 เปอร์เซ็นต์
  - ผลจริง P2: ผ่านกี่ TC จากทั้งหมดกี่ TC คิดเป็นกี่เปอร์เซ็นต์
  - ผ่านเกณฑ์หรือไม่: ผ่าน หรือ ไม่ผ่าน
- ข้อ 3: ไม่มีข้อบกพร่องคงค้างระดับ Critical หรือ Major (0 Open Critical Bugs ตามแผนหลัก และ Major ต้องไม่ค้างเช่นกัน)
  - จำนวน Bug ค้างระดับ Critical: ระบุจำนวนและเลข Bug ถ้ามี
  - จำนวน Bug ค้างระดับ Major: ระบุจำนวนและเลข Bug ถ้ามี
  - ผ่านเกณฑ์หรือไม่: ผ่าน หรือ ไม่ผ่าน
- ข้อ 4: เวลาตอบสนองจาก Locust ผ่านเกณฑ์ Cache Hit ไม่เกิน 3 วินาทีที่ p95 และ Full Inference ไม่เกิน 15 วินาทีที่ p90
  - ผลจริง Cache Hit p95: ระบุกี่วินาที
  - ผลจริง Full Inference p90: ระบุกี่วินาที
  - ผ่านเกณฑ์หรือไม่: ผ่าน หรือ ไม่ผ่าน
- ข้อ 5: ตารางสอบย้อนกลับครอบคลุม FR และ NFR ทั้งหมด FR ใดยังไม่มี TC ให้ระบุ GAP หรือ Deferred ชัดเจน
  - อ้างอิง rtm.md ฉบับวันที่ใช้ตรวจ: ระบุเวอร์ชันและวันที่
  - รายการ GAP/Deferred ตรงกับหัวข้อที่ 5 ของไฟล์นี้หรือไม่: ตรง หรือ ไม่ตรง

## 4. ความครอบคลุมขั้นต่ำ (Coverage ขั้นต่ำ อ้างอิง rtm.md ฉบับ Baseline 106 TCs)

- FR ภาพรวม 40 รายการ (ไม่นับ FR-SYS-11 ที่เป็น extra): Covered เต็ม 27 รายการ คิดเป็น 67.5 เปอร์เซ็นต์, นับรวม Partial 34 รายการ คิดเป็น 85.0 เปอร์เซ็นต์
- NFR 15 รายการ: Covered 13 รายการ คิดเป็น 86.7 เปอร์เซ็นต์, นับรวม Partial 15 รายการ คิดเป็น 100 เปอร์เซ็นต์
- เส้นทาง E2E 6 กระบวนการ: Covered 6 รายการ คิดเป็น 100 เปอร์เซ็นต์
- Manual TCs 106 รายการ (mobile 28, backend 24, ai 16, admin 17, e2e 6, nfr 15): ทุก ID มีที่อ้างใน RTM ไม่มี orphan
- เกณฑ์ขั้นต่ำสำหรับลงนามรอบนี้:
  1. ตัวเลข Covered เต็มต้องไม่ต่ำกว่า Baseline ข้างต้น ถ้าต่ำกว่าให้ระบุสาเหตุ
  2. รายการ Partial 7 รายการ (FR-INPUT-03, FR-INPUT-04, FR-SYS-08, FR-REPORT-01, FR-REPORT-06, FR-RPT-01, FR-AUDIT-01) ต้องมีหมายเหตุความเสี่ยงกำกับ
  3. รายการ Partial ด้าน NFR 2 รายการ (NFR-AI-01, NFR-AI-02 มี TC แล้วแต่ขาดชุดทดสอบมาตรฐาน) ต้องระบุว่ายอมรับความเสี่ยงหรือเลื่อน
  4. ผลรันจริงรอบนี้ต้องมีทั้ง execution_log ฝั่ง manual และรายงาน automate ฝั่ง server กับ mobile ถ้าฝั่ง admin หรือ model ยังว่าง (มีแค่ไฟล์คั่น) ให้บันทึกเป็นข้อจำกัดของรอบ

## 5. รายการ GAP และ Deferred ที่ยอมรับได้ (ต้องตรงกับ rtm.md)

- GAP 4 รายการ (ยังไม่มี TC):
  1. FR-SYS-01 ดึง EXIF และ Metadata: ยอมรับหรือไม่ยอมรับ พร้อมเหตุผลและแผน (เช่น เลื่อนเป็น Phase ถัดไป)
  2. FR-SYS-04 Reverse Image Search: ยอมรับหรือไม่ยอมรับ พร้อมเหตุผลและแผน
  3. FR-SYS-06 คัดกรองภาพสังเคราะห์ Generative AI: ยอมรับหรือไม่ยอมรับ พร้อมเหตุผลและแผน
  4. FR-ADM-03 Export ภาพ Scam ไปทำ Dataset: ยอมรับหรือไม่ยอมรับ พร้อมเหตุผลและแผน
- Deferred 2 รายการ (มี TC แต่รอทำ Phase 2):
  1. FR-AUTH-03 Google OAuth: ยอมรับการเลื่อนหรือไม่ พร้อมเงื่อนไข (เช่น ห้ามอ้างว่ารองรับ OAuth ในเอกสารปล่อย)
  2. FR-SYS-10 FCM Push Notification (TC-MOB-NOTIF-01, TC-NFR-FCM-01): ยอมรับการเลื่อนหรือไม่ พร้อมเงื่อนไข
- Partial ที่ต้องรับทราบความเสี่ยง 7 รายการ FR และ 2 รายการ NFR ตามหัวข้อที่ 4: ระบุทีละรายการว่ายอมรับหรือต้องแก้ก่อนปล่อย
- GAP ใหม่ที่พบนอกเหนือ rtm.md (ถ้ามี): ระบุ Requirement ID, TC ที่เกี่ยวข้อง, เหตุผล (เช่น เส้น cancelScan ไม่มี endpoint, category keys ไม่ตรงกัน, key safe ตกค้าง) และผู้รับทราบ

## 7. ผลการตัดสินรอบนี้ (เลือก 1 ค่า)

- ปล่อยได้โดยไม่มีเงื่อนไข: Exit Criteria ผ่านทุกข้อ และไม่มี GAP ใหม่
- ปล่อยได้แบบมีเงื่อนไข: ระบุเงื่อนไข (เช่น ต้องแก้ P2 ที่ค้างภายในกี่วัน ต้องเฝ้าระวัง latency หลังปล่อย ต้องห้ามประกาศฟีเจอร์ Deferred)
