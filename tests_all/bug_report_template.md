# แบบฟอร์มรายงานข้อบกพร่อง (Bug Report Template)

- โครงการ: ScamGuard (Scam Image Detection System)
- ตำแหน่งไฟล์: tests_all/bug_report_template.md
- อ้างอิงแผนหลัก: Document/tests_doc/test_plan/README.md ส่วนที่ 7 กระบวนการจัดการข้อบกพร่อง (Defect Management Lifecycle) และส่วนที่ 5 เกณฑ์การระงับและเริ่มใหม่
- อ้างอิงชุดทดสอบ: tests_all/manual_tests/test_cases_mobile.md, test_cases_backend.md, test_cases_ai_model.md, test_cases_admin.md, test_cases_e2e.md, test_cases_nfr.md
- อ้างอิงผลรัน: tests_all/tests_report/manual_tests/execution_log.md และ tests_all/tests_report/automate_tests
- สถานะก่อนสร้างไฟล์: ไม่พบไฟล์ bug report template ใน tests_all และ Document/tests_doc (ค้น severity, priority, Jira แล้วพบเฉพาะนิยามในแผนหลัก ยังไม่มีแบบฟอร์มให้กรอกจริง)

---

## 1. วิธีใช้แบบฟอร์มนี้

1. พบ Fail จาก execution_log.md ให้เปิด Bug 1 ฉบับต่อ 1 อาการ ห้ามรวมหลายอาการในใบเดียว
2. คัดลอกหัวข้อที่ 2 ทั้งหมดไปเป็นเนื้อหา Bug 1 ใบ แล้วกรอกทุกช่อง ห้ามเว้นช่อง Severity, Priority, Environment
3. ระบุ TC ID ที่ตรวจพบ และแถววันที่ใน execution_log.md เพื่อสอบย้อนกลับได้
4. แนบหลักฐานตามหัวข้อที่ 2.7 ทุกครั้งที่ทำได้ (ภาพหน้าจอ วิดีโอ ล็อก ส่วนต่างข้อมูล)
5. เดินสถานะตามวงจรชีวิตในหัวข้อที่ 3 ทุกครั้ง ห้ามข้ามจาก Resolved ไป Closed โดยไม่ผ่าน Verified
6. เมื่อเข้าสู่ Resolved ให้ทำ Retest ตามหัวข้อที่ 4 โดยผูก Bug ID เข้ากับ REG TC แล้วจึงปิดงาน

## 2. แบบฟอร์มให้คัดลอก (1 ใบต่อ 1 Bug)

### 2.1 หัวข้อบัตรงาน

- Bug ID: BUG-xxx (รันเลขต่อเนื่อง)
- หัวเรื่อง: อาการสั้นกระชับ ระบุโมดูลและสิ่งที่ผิด เช่น ผลสแกนแสดงระดับความเสี่ยงผิดช่วงบนหน้า Mobile
- TC ID ที่ตรวจพบ: เช่น TC-MOB-RES-01
- Requirement ID: เช่น FR-REPORT-01 (อ้างอิง tests_all/rtm.md ถ้าเป็น GAP ให้ระบุว่าเป็น GAP)
- วันที่พบ: ปปปป-ดด-วว
- ผู้พบ: ชื่อผู้ทดสอบ
- ผู้รับผิดชอบ: ชื่อผู้พัฒนา (กรอกเมื่อ Assigned)
- สถานะปัจจุบัน: New / Assigned / In Progress / Resolved / Verified / Closed / Rejected / Reopened (เลือก 1 ค่า ตามหัวข้อที่ 3)

### 2.2 ระดับความรุนแรง (Severity เลือก 1 ค่า ตามแผนหลัก)

- Critical วิกฤต: ระบบแครช ข้อมูลสูญหาย ความปลอดภัยรั่วไหล ไม่สามารถสแกนภาพได้เลย
- Major รุนแรง: ฟังก์ชันหลักทำงานผิดพลาด เช่น Heatmap แสดงพิกเซลผิดตำแหน่ง คำนวณคะแนนความเสี่ยงผิดช่วงระดับ
- Medium ปานกลาง: ปัญหาการแสดงผล UI บิดเบี้ยว ปัญหาการสลับภาษาบางจุด การกรองรายงานไม่ตรงเงื่อนไข
- Minor เล็กน้อย: ปัญหาการสะกดคำ ความคลาดเคลื่อนของสีคอนทราสต์เล็กน้อยที่ไม่กระทบการใช้งานหลัก
- ค่าที่เลือก: ระบุ 1 ค่า พร้อมเหตุผลสั้น 1 บรรทัดว่าทำไมจึงอยู่ระดับนี้

### 2.3 ลำดับความสำคัญในการแก้ไข (Priority เลือก 1 ค่า ตามแผนหลัก)

- P0 Blocker: ต้องแก้ไขทันที หยุดการปล่อยเวอร์ชัน (สอดคล้อง Suspension Criteria กรณีเจอ P0 ต้องระงับการทดสอบ)
- P1 High: ต้องแก้ไขก่อนปล่อยเวอร์ชันสู่ผู้ใช้งาน
- P2 Medium: สามารถจัดเข้าคิวแก้ไขใน Sprint ถัดไป
- P3 Low: แก้ไขเมื่อมีเวลาว่างหรือรอบปรับปรุงความประณีต
- ค่าที่เลือก: ระบุ 1 ค่า พร้อมเหตุผลว่าเหตุใดจึงต้องแก้ในรอบนี้หรือเลื่อนได้

### 2.4 ขั้นตอนทำซ้ำ (Steps to Reproduce กรอกเป็นลำดับเลข)

1. เตรียมข้อมูลและสภาพแวดล้อมตาม Pre-conditions ของ TC ID นั้น (ระบุข้อมูลทดสอบที่ใช้ เช่น อีเมลทดสอบ ไฟล์ภาพทดสอบ)
2. ขั้นที่ 1: ระบุการกระทำทีละขั้นพร้อมตำแหน่งหน้าจอหรือเส้น API เช่น กดปุ่มสแกนบนหน้า Home หรือยิง POST ไปที่เส้นสแกนหลัก
3. ขั้นที่ 2: ระบุต่อเนื่องจนถึงจุดที่พบอาการ
4. ขั้นที่ 3: ระบุความถี่ที่ทำซ้ำได้ เช่น เกิดทุกครั้ง 3 ใน 5 ครั้ง หรือเกิดเฉพาะไฟล์เกิน 10MB
5. ผลที่สังเกตเห็น: บรรยายอาการที่เกิดจริงตรงจุดนี้ก่อน แล้วไปเทียบ Expected กับ Actual ในหัวข้อถัดไป

### 2.5 ผลที่คาดหวังเทียบกับผลจริง (Expected vs Actual)

- ผลที่คาดหวัง: คัดลอก Expected Results ของ TC นั้นมา เช่น ได้รหัสตอบกลับ 201 และ Response มี id email full_name role โดยไม่มีรหัสผ่าน plain text, หรือคะแนน 0-39 ต้องแสดงระดับ Low
- ผลจริง: บรรยายสิ่งที่ระบบทำจริง เช่น ได้รหัส 500, หรือคะแนน 35 แต่แสดงระดับ Medium, หรือ Heatmap เลื่อนจากตำแหน่งจริง
- ส่วนต่างสำคัญ: สรุปความต่าง 1-2 บรรทัด เช่น คาดหวัง 201 แต่ได้ 500, คาดหวัง Low แต่ได้ Medium

### 2.6 สภาพแวดล้อมที่พบ (Environment กรอกทุกช่อง)

- ฝั่งที่พบ: Mobile / Backend API / AI Pipeline / Admin Portal / E2E ข้ามระบบ (เลือกที่ตรง)
- อุปกรณ์หรือเบราว์เซอร์: เช่น Pixel 6 Android 14, Galaxy S21, Emulator API 33 หรือ 34, Chrome รุ่นที่ใช้ (อ้างอิง Test Bed ในแผนหลักส่วนที่ 4)
- เวอร์ชันแอปและบิลด์: ระบุบิลด์ Mobile, คอมมิต Backend, เวอร์ชันโมเดล (เช่น โมเดลก่อนหรือหลัง Deploy)
- ฝั่งเซิร์ฟเวอร์: Backend Port 8000, PostgreSQL 15 Port 5432, Redis 7 Port 6379, Admin Portal Port 5173, Timezone Asia Bangkok
- ข้อมูลทดสอบ: อีเมลทดสอบ ไฟล์ภาพที่ใช้ ขนาดไฟล์ ชนิดไฟล์ (ห้ามใช้ข้อมูลผู้ใช้จริง ต้องสอดคล้อง PDPA)
- เครือข่าย: ออนไลน์ปกติ ออฟไลน์ หรือเครือข่ายจำลอง

### 2.7 หลักฐานประกอบ (Attachments)

- ภาพหน้าจอหรือวิดีโอ: แนบทุกรายการ UI ถ้าทำได้ วงตำแหน่งที่ผิดให้เห็นชัด
- ล็อกและร่องรอย: แนบข้อความล็อกหรือ Stack Trace ที่เกี่ยวข้อง ระบุเวลาเกิดเหตุ Timezone Asia Bangkok
- ข้อมูลคำขอและคำตอบ: แนบ Payload และ Response ที่ตัดข้อมูลอ่อนไหวออกแล้ว
- ไฟล์ทดสอบ: ระบุชื่อไฟล์ภาพที่ใช้ ถ้าเป็นไฟล์เฉพาะให้เก็บในตำแหน่งที่ทีมเข้าถึงได้และอ้างชื่อไว้
- ถ้าไม่มีหลักฐานข้อใด ให้เขียนว่าไม่มีพร้อมเหตุผล ห้ามเว้นว่างโดยไม่อธิบาย

### 2.8 ผลกระทบและการประเมินเบื้องต้น

- ผลกระทบต่อผู้ใช้: ระบุว่าใช้งานต่อได้หรือไม่ ต้องใช้ทางอ้อมใด
- ผลกระทบต่อข้อมูล: ระบุว่ามีข้อมูลสูญหายหรือค้างในฐานข้อมูลหรือไม่ (เช่น ตาราง users, consent_logs, audit_log, ประวัติสแกน)
- ความถี่: เกิดทุกครั้ง เกิดบางครั้ง หรือเกิดเฉพาะเงื่อนไขพิเศษ
- งานที่ถูกบล็อก: ระบุ TC อื่นที่ทดสอบต่อไม่ได้เพราะ Bug นี้ (เชื่อมกับสถานะ Blocked ใน execution_log.md)

## 3. วงจรชีวิตของ Bug (ต้องตรงกับแผนหลัก ส่วนที่ 7.3)

- สถานะมาตรฐาน: New ไป Assigned ไป In Progress ไป Resolved ไป Verified ไป Closed
- เส้นทางปฏิเสธ: จาก In Progress ไป Rejected ได้เมื่อพิสูจน์ว่าไม่ใช่ข้อบกพร่อง (เช่น ทดสอบผิดขั้นตอน เป็น GAP ที่ต้องเปิด TC ใหม่ หรือเป็นพฤติกรรมตามออกแบบ) ต้องเขียนเหตุผลการปฏิเสธและผู้ตัดสิน
- เส้นทางเปิดซ้ำ: จาก Verified ไป Reopened ได้เมื่อ Retest ไม่ผ่าน แล้ววนกลับไป In Progress ใหม่ ห้ามเปิด Bug ใบใหม่ซ้ำอาการเดิม ให้ใช้เลขเดิมแล้วเพิ่มรอบ Retest
- กฎการเปลี่ยนสถานะ:
  1. New: ผู้ทดสอบเปิดใบใหม่พร้อมกรอกครบทุกช่องในหัวข้อที่ 2
  2. Assigned: หัวหน้าทีมมอบหมายผู้แก้ไขและทบทวน Severity กับ Priority
  3. In Progress: ผู้พัฒนาเริ่มแก้ไข บันทึกสาเหตุรากและไฟล์ที่แก้
  4. Resolved: ผู้พัฒนาแก้เสร็จ ระบุคอมมิต บิลด์ที่แก้ และวิธีตรวจสอบซ้ำ
  5. Verified: QA ทำ Retest ตามหัวข้อที่ 4 แล้วผ่านจึงเปลี่ยนเป็น Verified
  6. Closed: หัวหน้า QA หรือผู้ปล่อยเวอร์ชันตรวจว่า Retest ผ่านและ Regression ที่เกี่ยวข้องผ่านแล้วจึงปิด
  7. Rejected: ตัดสินว่าไม่ใช่ Bug พร้อมเหตุผล แล้วปิดเส้นทางนี้โดยไม่ต้อง Retest
  8. Reopened: Retest ไม่ผ่าน ให้ส่งกลับพร้อมหลักฐานรอบ Retest

## 4. ขั้นตอน Retest และ Regression (ผูก Bug เข้ากับการทดสอบซ้ำก่อนปิด)

ส่วนนี้เติมเต็มช่องว่างของขั้นที่ 6: ปัจจุบันมี REG TCs แล้ว ได้แก่ TC-BE-REG-01 (ประวัติเดิมยังอ่านได้หลัง Deploy โมเดล), TC-MOB-REG-01 (ประวัติเดิมยังเปิดได้หลังอัปเดตแอป), TC-E2E-REG-09 (สแกนซ้ำหลังขึ้นโมเดลใหม่ผลคงเดิม), และ TC-AI-REG-01 (เทียบโมเดลใหม่กับโมเดลเดิม) แต่ยังขาดกระบวนการผูก Bug เข้ากับการทดสอบซ้ำ จึงกำหนดขั้นตอนดังนี้

1. เมื่อ Bug เปลี่ยนเป็น Resolved ให้สร้างแถว Retest ใหม่ใน tests_all/tests_report/manual_tests/execution_log.md โดยช่อง TC ID ใส่ TC เดิมที่พบ Bug และช่องหมายเหตุใส่เลข Bug ID พร้อมคำว่า Retest ครั้งที่ 1
2. รัน TC เดิมซ้ำทุกข้อตาม Steps to Reproduce ถ้าผ่านให้เปลี่ยน Bug เป็น Verified ถ้าไม่ผ่านให้เปลี่ยนเป็น Reopened แล้วกลับไปข้อ 1 โดยเพิ่มครั้งที่ Retest
3. เมื่อ Verified แล้ว ให้เลือกรัน REG TC ที่เกี่ยวข้องอย่างน้อย 1 รายการ:
   - ถ้าแก้ Backend หรือ Deploy หรือ Rollback โมเดล: รัน TC-BE-REG-01
   - ถ้าแก้ Mobile หรืออัปเดตแอป: รัน TC-MOB-REG-01
   - ถ้าเปลี่ยนโมเดลแล้วกระทบทั้งระบบ: รัน TC-E2E-REG-09
   - ถ้าเทียบพฤติกรรมโมเดลใหม่กับโมเดลเดิม: รัน TC-AI-REG-01
4. บันทึกผล REG TC ลง execution_log.md อีกแถว โดยช่องหมายเหตุผูกเลข Bug ID เดิมพร้อมคำว่า Regression
5. ถ้า REG TC ใด Fail ให้เปิด Bug ใหม่ (เลขใหม่) แล้วอ้าง Bug เดิมในหมายเหตุ ห้ามถือว่า Bug เดิมผ่าน
6. ปิด Bug เดิมเป็น Closed ได้เมื่อ TC เดิม Retest ผ่าน และ REG TC ที่เลือกผ่านครบแล้วเท่านั้น
